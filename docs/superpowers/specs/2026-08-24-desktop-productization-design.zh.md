# DeepSeek Harness 桌面产品化设计

[English](2026-08-24-desktop-productization-design.md) | 中文

## 范围

本设计覆盖 `apps/desktop`、桌面发行工作流、上游同步记录，以及 CLI（命令行界面）和 Web 进入桌面安装包所需的最小根配置。CLI 的业务行为、Web 产品界面和独立 Node 后端的进程模型不在改造范围内。

## 目标

- Windows 用户只安装一次 NSIS 安装版，后续在应用内检查、下载并重启完成更新。
- GitHub Fork 根据桌面版本标签自动构建、验证和发布，无需维护者在本机打包。
- Electron 启动后立即显示真实启动状态，后端就绪后在同一窗口进入主界面。
- 关闭主窗口只隐藏窗口，托盘保持后端运行；显式“退出”命令停止后端并结束应用。
- 正式发布只包含安装包和更新元数据，不发布单文件便携版、展开目录或构建诊断文件。
- 在保留独立 Node、终端、原生模块和子进程行为的前提下，减少安装体积和文件数量。
- 打包后的应用验证完整的生产运行时清单，并在所有 Windows 集成位置使用同一套已批准图标。
- 每个桌面版本记录同步到 fork 的准确官方上游提交与源码版本，同时保持 fork 基于源码的依赖方式。
- 桌面专属改动集中在 `apps/desktop`，降低同步上游 CLI 和 Web 代码时的冲突。

## 非目标

- 不把后端迁移到 Electron 的 Node 运行时，不在 Electron 主进程中托管后端，也不以 Electron `runAsNode` 取代独立 Node。
- 不重写现有 Web 界面，也不在 Web 页面中加入桌面更新组件。
- 不实现便携版的原地更新。
- 不承诺在没有 Windows 代码签名证书时消除 SmartScreen 提示。
- 不改变会话、用户设置和凭据的持久化位置或格式。
- 不引入 Git submodule，也不以已发布的 `@deepseek-ai/dsh-*` 运行时包取代 `workspace:^` 依赖。
- 不加入 profile 切换、最后健康 profile 回滚，也不自动修改或回滚源码、profile、插件或用户数据。
- 不加入插件市场、社区集成层或手机远程控制。
- 不在 Windows 登录时自动启动。
- 首版不加入后台任务完成通知。
- 不加入独立的更新网站或更新 API；更新源保持为 fork 的 GitHub Releases 和 `electron-updater`。

## 组件

### 桌面主进程

桌面主进程继续拥有单实例锁、窗口、托盘、后端进程和退出顺序。主进程在 Electron 就绪后立即创建主窗口并加载本地启动页面，同时启动后端；后端打印就绪 URL 后，主进程在同一窗口加载该 URL。窗口安全配置继续启用上下文隔离、禁用 Node 集成并启用渲染器沙箱。

### 启动页面

启动页面及其图标作为桌面壳静态资源进入 `app.asar`。页面只显示版本号和真实阶段文本，不显示无法由实际进度支撑的百分比。阶段至少包括“正在启动本地服务”和“正在加载界面”。后端退出、启动拒绝或 90 秒内未就绪时，主进程提供重试、导出诊断、打开日志目录和退出操作。

### 后端启动器

后端启动器继续使用随安装包提供的标准 Node，并执行已构建的 `@deepseek-ai/dsh` CLI。打包阶段把后端依赖闭包物化到 `resources/backend`，使标准 Node 不读取 `app.asar`。桌面壳从 `app.asar` 运行，后端从真实文件系统运行。

打包运行时闭包验证清点 CLI 入口、Web 静态资源、独立 Node 可执行文件、Windows x64 原生二进制、更新模块与配置、启动页面、托盘资源、应用图标资源、生产依赖闭包和生产许可证声明。缺少运行文件、包含错误平台文件或依赖仅能从源码解析时，发布工作流拒绝发布安装包。

### 托盘与窗口生命周期

只有后端就绪且主渲染器完成加载后才创建托盘。托盘存在时，关闭主窗口会阻止默认关闭并隐藏同一窗口，不停止后端；左键单击托盘会恢复并聚焦窗口，启动第二实例也执行同样操作。

托盘菜单包含“显示”“检查更新”“导出诊断”和“退出”，托盘提示文字包含产品名和桌面版本。通过托盘或应用菜单退出，以及“重启更新”，都会先设置 `isQuitting`，再有序停止后端。Windows 关机和普通应用退出也正常结束。如果托盘创建失败，应用仍可使用，关闭窗口会退出而不是隐藏，并且应用菜单仍提供带 Ctrl+Q 快捷键的“文件 > 退出”。

### 更新管理器

更新管理器封装 `electron-updater`，只在已安装的生产构建中启用。应用主菜单和托盘均提供“检查更新”；后台检查在主界面和托盘就绪后执行。后台检查失败只记录日志，用户手动检查失败则显示可重试错误。

更新状态依次为检查、可用、下载、已下载和失败。发现新版本时，原生对话框提供“下载更新”和“稍后”；下载进度同步到 Windows 任务栏；下载完成后提供“重启更新”和“稍后”。重启安装前先正常停止后端，再调用更新器退出并安装。校验或安装准备失败时保留当前安装，不覆盖可运行版本。

### 上游同步基线

`apps/desktop/upstream.json` 通过 `repository`、`commit`、`sourceVersion` 和 `desktopVersion` 记录官方仓库 URL、最后同步到 fork 的 40 位上游提交、上游源码版本和桌面版本。记录的提交是已经合并进 fork 的官方上游提交，不是 fork 当前的 `HEAD`。

发布工作流要求 `desktopVersion` 等于 `apps/desktop/package.json` 中的版本，`sourceVersion` 等于 fork 根目录的产品版本，并要求 `commit` 存在且是发布提交的祖先。官方源码仍通过常规同步或合并进入 fork；CLI、Web 和桌面构建仍使用 fork 工作区源码与 `workspace:^` 依赖。

### 图标资源流水线

一个已获许可或以其他方式批准的产品图标源生成 Windows ICO、窗口 PNG 和托盘变体。构建验证生成的图标身份已用于主可执行文件、NSIS 安装器、已安装快捷方式、BrowserWindow、启动页面和托盘。公开 fork 仅在许可证与品牌规则允许时使用上游品牌，并且不暗示官方认可。

### 日志与诊断

桌面主进程和后端启动输出写入 Electron 用户日志目录。日志按每个文件 10 MiB 轮转，启动时删除七天前的文件，并从最旧的轮转文件开始删除，使应用自有日志总量不超过 200 MiB。日志记录桌面版本、上游同步基线、启动阶段、后端退出信息、更新状态和托盘生命周期，但绝不记录环境变量、凭据、用户输入、提示词或会话内容。

托盘和启动失败界面均提供“导出诊断”。原生隐私警告出现后，保存对话框才会创建 ZIP；ZIP 只包含近期自有日志、启动标记、桌面与上游版本，以及操作系统、Electron 和 Node 版本信息。归档排除凭据和会话内容，对话框提示用户在分享前检查文件。

### 启动健康状态与恢复

应用启动时先读取已有的活动运行标记，再以记录版本、上游基线与启动阶段的小型标记替换它。只有后端就绪且主渲染器完成加载后，运行才被标记为健康，同时记录最后健康的桌面版本、上游基线和时间戳。仅当本次运行已达到健康状态并有序退出时才删除标记；发现上次遗留标记或本次启动连续失败两次时，恢复界面提供重试、导出诊断、打开日志和退出操作。

恢复过程绝不改变 profile、插件、会话、凭据、用户数据或已同步源码。最后健康记录只提供诊断证据，不是 profile 检查点，也不触发自动回滚。

## 启动与退出流程

1. 获取单实例锁；第二实例恢复并聚焦现有窗口，包括窗口已经隐藏的情况。
2. Electron 就绪后设置 Windows AppUserModelID、已批准图标和应用菜单，然后创建活动运行标记。
3. 创建并显示加载本地启动页面的窗口。
4. 启动独立 Node 后端，并把标准输出和错误输出写入轮转日志。
5. 后端就绪后在同一窗口加载回环 URL。
6. 主渲染器完成加载后，把本次运行标记为健康，更新最后健康记录并创建托盘。
7. 托盘就绪后执行一次后台更新检查。
8. 托盘可用时，关闭主窗口只隐藏窗口并保持后端运行。
9. 显式退出、Windows 关机或更新重启先设置退出状态，再请求后端正常结束，并只在超过现有宽限期后强制结束。
10. 达到健康状态的运行有序退出时，在应用结束或重启前删除活动运行标记。

## 发布与版本

桌面应用使用独立语义版本，Git 标签格式为 `desktop-v<version>`。工作流验证标签版本与 `apps/desktop/package.json` 和 `apps/desktop/upstream.json` 一致，不一致时停止发布。上游源码版本可以独立变化，不直接触发桌面客户端升级。

官方源码同步路径保持为 `deepseek-ai/deepseek-harness` 到用户的 GitHub fork，再由 fork 保留的 `apps/desktop` 完成构建。上游同步准备过程把 `apps/desktop/upstream.json` 更新为该次同步包含的最后一个官方提交。该记录增加发布可追溯性，既不下载源码，也不阻止后续同步。

Windows 发布工作流在 `desktop-v*` 标签上运行，并授予最小的 `contents: write` 权限。工作流在 Windows runner 上安装锁定依赖，验证标签与上游记录，构建 CLI、Web 和桌面端，运行聚焦测试与打包运行时闭包验证，然后生成 NSIS 安装包。所有验证通过后，工作流创建 GitHub Release 并上传安装包、`latest.yml` 和安装包 `.blockmap`；更新源由当前工作流仓库身份生成，因此 fork 所有者和仓库名不硬编码在源文件中。

现有无更新器版本需要手动安装一次首个产品化安装包。此后安装包使用相同 appId、安装标识和用户数据位置，更新器在原安装位置升级。发布工作流预留 electron-builder 标准代码签名环境变量；存在签名 Secrets 时自动签名，不存在时生成可测试的未签名个人构建。

## 打包与体积

electron-builder 只配置 NSIS 目标。`win-unpacked` 可以作为构建中间目录用于测试，但不上传到 Release；portable 目标、旧便携 EXE 和公开构建诊断文件退出发行流程。已安装应用直接从安装文件启动，每次启动都不会执行单文件载荷解包。

桌面壳进入 `app.asar`，独立 Node 和后端依赖闭包进入 `extraResources`。首轮裁剪排除 source map、TypeScript 构建信息、测试资产、示例资产和非 Windows x64 原生二进制。首轮不全局删除 `.ts` 文件；只有打包运行时清单证明文件不在运行时解析路径、且打包后启动测试覆盖其使用方时，才增加更窄的排除规则。

构建输出生成体积报告，分别记录安装包大小、展开大小、文件数量和最大的运行时目录。相对于当前基线，展开安装体积至少减少 50 MiB，安装包至少减少 5 MiB；达不到目标时发布检查失败并保留报告，不通过删除未经验证的运行依赖达标。

## 错误处理与安全

- 自动更新仅接受 electron-builder 元数据中匹配的版本、路径和 SHA-512；下载失败允许重试。
- 开发模式默认禁用更新，并支持环境变量显式禁用生产更新检查，便于离线和故障诊断。
- 外部导航继续交给系统浏览器，回环 URL 以外的导航不进入应用窗口。
- 更新下载不获得 Web 页面中的凭据或 Node 权限；更新控制留在 Electron 主进程。
- 代码签名是可信公开发行的发布要求，但不是本地功能验证的前置条件。未签名构建明确标记为个人测试构建。
- 构建诊断文件包含构建机路径，不上传到公开 Release。
- 诊断导出使用明确内容允许清单并显示原生隐私警告，绝不收集凭据、提示词、会话内容或任意用户文件。
- 托盘创建失败时禁用关闭隐藏，并保留可见退出路径，避免应用隐藏后无法退出。
- 恢复过程只展示证据与用户操作，绝不修改或回滚 profile、插件、会话、用户数据或已同步源码。

## 测试

单元测试覆盖启动 URL 解析、后端就绪和失败、重复结算防护、更新状态转换、后台与手动检查的错误差异、菜单命令和退出更新顺序。启动页面测试验证真实状态文本与恢复操作，不依赖虚假计时。

托盘生命周期测试覆盖菜单命令、关闭隐藏、左键恢复与聚焦、第二实例恢复、显式退出、更新重启、后端停止和托盘创建失败回退。

诊断测试覆盖日志轮转、七天保留期、200 MiB 上限、活动运行标记转换、最后健康记录、非正常启动恢复、ZIP 允许清单，以及凭据、提示词和会话内容排除。

打包后测试直接使用随包 Node 启动随包 CLI，等待 Web 就绪行并请求回环 URL，随后验证正常退出。测试还检查打包运行时清单的每个类别、生产许可证声明、Windows x64 原生模块集合，以及可执行文件、安装器、快捷方式、窗口、启动页面和托盘的图标配置。

发布验证会拒绝标签、桌面包版本、上游源码版本、上游提交祖先关系或更新元数据不一致。工作流在发布 Release 前证明安装包和更新元数据指向相同的安装包字节。

真实更新验收发布两个连续测试版本：旧版本发现新版本、下载、重启安装，并在新版本中保留用户设置、会话和自定义安装位置。没有可用新版本、网络中断、下载失败和用户选择稍后的路径也必须保持当前版本可用。

## 验收标准

- 双击安装后的快捷方式后立即出现带正确图标和版本号的加载窗口。
- 后端就绪后同一窗口进入主界面，CLI、Web、终端、文件操作和退出行为保持正常。
- 关闭主窗口后窗口隐藏、后端保持可用，托盘恢复并聚焦同一窗口。
- 从托盘或带 Ctrl+Q 快捷键的“文件 > 退出”显式退出会停止后端并结束应用；托盘初始化失败时仍有可用退出路径。
- 主渲染器达到健康状态后，托盘提供“显示”“检查更新”“导出诊断”和“退出”。
- GitHub Actions 可从桌面标签独立完成构建、验证和发布。
- GitHub Release 只包含 NSIS 安装包、`latest.yml` 和 `.blockmap`。
- 应用可以后台和手动检查更新，用户通过下载与重启按钮完成升级。
- 更新失败不会损坏当前安装，升级保留用户数据和安装位置。
- “导出诊断”显示隐私警告，生成定义的允许清单，并排除凭据、提示词、会话内容和任意用户文件。
- 每个 Release 标明官方仓库、已同步上游提交、源码版本和桌面版本；记录不一致或提交不是祖先时，工作流拒绝发布。
- 主可执行文件、NSIS 安装器、已安装快捷方式、窗口、启动页面和托盘显示已批准的产品图标变体。
- portable 目标与旧便携 EXE 被清理，展开目录只作为短期测试产物。
- 展开体积和安装包分别达到 50 MiB 与 5 MiB 的最小降幅。
- 打包运行时闭包验证覆盖 CLI、Web 资源、独立 Node、Windows x64 原生模块、更新器、启动页面、托盘与图标资源、生产依赖和许可证声明。
- 聚焦单元测试、类型检查、文档检查、构建检查和打包后启动测试通过。
